# Форма ввода заказа: инструкции и стандарты

Версия: 1.0  
Статус: рабочий стандарт для проектирования и разработки  
Область: создание и редактирование заказа менеджером

## 1. Цель

Форма должна позволять менеджеру быстро занести заказ, не переключаясь между карточкой заказа, отдельным экраном строк и модальными окнами. Пользовательский сценарий должен быть близок к работе в Excel:

- данные вводятся слева направо и сверху вниз;
- ячейки редактируются непосредственно в таблице;
- клавиатура является полноценным способом работы;
- расчётные значения видны сразу;
- вставка диапазона из Excel сохраняет структуру строк;
- результат каждого действия понятен без перезагрузки страницы.

Этот документ задаёт поведение, структуру, визуальные правила, валидации и критерии приёмки. Формулировки «должно» и «нельзя» являются обязательными требованиями; «рекомендуется» — предпочтительное решение, допустимое к изменению только с обоснованием.

## 2. Базовые решения

### 2.1. Один экран и один компонент

Создание и редактирование используют один экран и одну реализацию формы:

```text
OrderFormPage(mode: "create" | "edit", order?: Order)
```

Различия режима:

| Сценарий | URL | Начальные данные | Основная кнопка |
|---|---|---|---|
| Новый заказ | `/orders/new` | пустые значения, статус `draft` | «Сохранить черновик» |
| Редактирование | `/orders/:id/edit` | данные заказа и строки | «Сохранить» |

После первого сохранения нового заказа сервер возвращает `id`, а приложение делает `replace` на `/orders/:id/edit`, не сбрасывая введённые значения и позицию курсора. Пользователь остаётся на том же экране.

### 2.2. Заказ и строки сохраняются атомарно

Кнопка сохранения отправляет реквизиты и изменённые строки одним логическим действием. Сервер либо сохраняет всё, либо не меняет заказ. При сетевой ошибке введённые значения остаются в форме и доступны для повторной отправки.

### 2.3. Черновик и подтверждение — разные действия

Сохранение черновика не меняет статус автоматически. Переход статуса выполняется отдельным контролом в шапке и всегда показывает текущее состояние. Удаление или отмена заказа не является частью обычного сохранения и требует отдельного подтверждения.

### 2.4. Автосохранение без потери контроля

Для черновика используется debounce-автосохранение изменённых полей через 800–1200 мс после прекращения ввода или при уходе из ячейки. В шапке показываются состояния:

- «Есть несохранённые изменения»;
- «Сохранение…»;
- «Сохранено в 14:32»;
- «Не удалось сохранить — повторить».

Клавиши `Ctrl+S`/`Cmd+S` выполняют немедленное полное сохранение. Для заказов в статусах `closed` и `cancelled` форма только для чтения.

## 3. Информационная архитектура страницы

Страница имеет одну вертикальную рабочую область. Вкладки, аккордеоны и модальные окна для основных данных заказа не используются.

```text
┌ Шапка: назад · № заказа · статус · сохранение · действия ┐  sticky
├ Реквизиты заказа и заказчик                              ┤
├ Сроки и доставка                                         ┤
├ Параметры изделия                                        ┤
├ Табличная часть (Excel-like grid)                       ┤
├ Итоги заказа                                             ┤
├ Оплаты и остаток                                         ┤
└ Нижняя панель действий                                   ┘  sticky
```

### 3.1. Шапка

Шапка закрепляется при прокрутке (`position: sticky; top: 0`) и содержит:

1. хлебную крошку «Заказы / Новый заказ» или «Заказы / №…»;
2. номер спецификации/заказа и короткое имя заказчика;
3. цветной бейдж текущего статуса;
4. индикатор сохранения;
5. действия: «Сохранить», «Печать», «Экспорт Excel», «Ещё».

В режиме нового заказа вместо номера показывается «Новый заказ». Не показывать технический UUID.

### 3.2. Реквизиты заказа и заказчик

Секция открыта по умолчанию. Поля размещаются в логическом порядке, а не по алфавиту:

1. номер спецификации;
2. дата оформления;
3. заказчик;
4. тип клиента;
5. основной комментарий.

Номер и дата — в первой строке. Заказчик занимает не менее двух колонок на широком экране. Поиск заказчика — поле с подсказками и поиском по имени, телефону и ИНН; выбор существующего заказчика не должен требовать перехода на другую страницу.

### 3.3. Сроки, производство и доставка

Поля:

- «В производство»;
- «Плановая готовность»;
- «Нужна доставка»;
- «Адрес доставки» (видим и обязателен только при включённой доставке);
- контакт получателя и комментарий к доставке, если эти данные поддерживаются моделью.

При включении доставки адрес появляется без скачка страницы и получает фокус только по явному запросу пользователя. При выключении адрес не удаляется молча: значение очищается только после подтверждения либо сохраняется как черновое неактивное значение.

### 3.4. Параметры изделия

Поля:

- категория;
- материал;
- фрезеровка;
- толщина, мм;
- цвет/код цвета;
- стыковка;
- примечание.

Справочные значения выбираются из активных справочников. Текущее неактивное значение в старом заказе всё равно отображается и помечается «неактивно», чтобы редактирование не изменяло данные без ведома пользователя.

### 3.5. Табличная часть

Табличная часть находится на той же странице сразу после реквизитов. Она не открывается в отдельном маршруте.

Обязательные возможности:

- добавление группы, товарной строки, услуги, комментария и пустой строки;
- редактирование каждой ячейки без модального окна;
- изменение порядка строк и перенос строки между группами;
- удаление строки с возможностью отменить действие в течение 5 секунд;
- сворачивание/разворачивание групп;
- отображение итогов группы и заказа;
- вставка табличного диапазона из Excel;
- копирование выделенного диапазона в буфер обмена в TSV;
- горизонтальная прокрутка на узких экранах.

### 3.6. Итоги, оплаты и история

Сразу под таблицей показывается блок итогов: площадь, сумма до корректировок, скидка, наценка, итоговая сумма, оплачено и остаток. Итоги не прячутся в отдельную вкладку и обновляются при каждом изменении строки.

Оплаты — компактная таблица под итогами. Добавление платежа выполняется inline-строкой с датой, типом, методом, суммой и комментарием. История статусов доступна из шапки через раскрываемый popover или боковую панель; переход на отдельную страницу для проверки истории не требуется.

## 4. Стандарт Excel-like таблицы

### 4.1. Колонки

Порядок колонок фиксированный и одинаковый для просмотра, ввода, экспорта и печати:

| № | Поле | Ввод | Расчёт/вывод | Формат |
|---:|---|---|---|---|
| 1 | Тип строки | да | нет | группа / товар / услуга / комментарий / пустая |
| 2 | Высота, мм | да для товара | нет | число, до 2 знаков |
| 3 | Ширина, мм | да для товара | нет | число, до 2 знаков |
| 4 | Количество | да | нет | число, до 3 знаков |
| 5 | Ед. | да/справочник | нет | `шт.`, `м²`, `компл.` и т. п. |
| 6 | Описание | да | нет | текст |
| 7 | Цена за м² | да для товара | нет | денежное, 2 знака |
| 8 | Площадь 1 ед. | нет | `height × width / 1 000 000` | м², 4–6 знаков |
| 9 | Общая площадь | нет | `площадь 1 ед. × количество` | м², 4 знака |
| 10 | Цена за ед. | нет/да для услуги | расчёт для товара | деньги, 2 знака |
| 11 | Сумма | нет | `цена за ед. × количество` | деньги, 2 знака |
| 12 | Действия | нет | нет | удалить / меню строки |

Колонки 1, 4, 6 и 11 должны оставаться доступными при горизонтальной прокрутке. Заголовок таблицы закрепляется внутри области таблицы. Денежные и числовые колонки выравниваются по правому краю; текстовые — по левому.

### 4.2. Плотность и размеры

- высота строки: 36 px в обычном режиме, 44 px на touch-устройствах;
- высота заголовка: 40 px;
- горизонтальные отступы ячейки: 8–12 px;
- размер шрифта таблицы: 13–14 px;
- активная ячейка имеет заметный контур 2 px, но не меняет ширину таблицы;
- расчётные ячейки имеют нейтральный фон и доступны для копирования, но не для ввода;
- строка группы визуально отличается фоном, жирным названием и итогом справа.

Не использовать микроскопический текст, иконки без подсказки или чрезмерные разделители, из-за которых таблица выглядит как бухгалтерский отчёт.

### 4.3. Клавиатура

| Клавиша | Поведение |
|---|---|
| `Tab` | перейти в следующую редактируемую ячейку; в последней ячейке последней строки добавить новую строку |
| `Shift+Tab` | перейти в предыдущую ячейку |
| `Enter` | сохранить текущую ячейку и перейти вниз в той же колонке |
| `Shift+Enter` | сохранить и перейти вверх |
| `Arrow keys` | перемещаться по ячейкам, если поле не использует стрелки для выбора текста |
| `F2` / двойной клик | открыть редактирование выбранной ячейки |
| `Esc` | отменить изменения текущей ячейки до последнего сохранённого значения |
| `Delete` | очистить значение; удаление строки выполняется отдельной командой |
| `Ctrl+C` / `Ctrl+V` | копировать/вставлять одну ячейку или диапазон TSV |
| `Ctrl+S` | сохранить весь заказ |
| `Ctrl+Enter` | сохранить строку и остаться в ней |

После добавления строки фокус устанавливается в первую полезную ячейку, обычно «Высота» или «Описание» в зависимости от типа строки. Фокус никогда не переносится в начало страницы.

### 4.4. Вставка из Excel

При вставке TSV:

1. определить число строк и колонок;
2. показать лёгкий предпросмотр прямо над таблицей;
3. сопоставить колонки по заголовкам, а при отсутствии заголовков — по фиксированному порядку;
4. подсветить ошибки по ячейкам;
5. применить импорт только после «Вставить» или `Ctrl+Enter` в предпросмотре.

Пустые строки в исходном диапазоне сохраняются как строки типа `empty`, если пользователь не выбрал «Пропускать пустые строки». Текст с табуляцией внутри кавычек не должен разрушать структуру вставки.

### 4.5. Добавление и удаление строк

Кнопка «+ Строка» открывает компактное меню типа строки, а не модальное окно. Команды «Группа», «Товар», «Услуга», «Комментарий», «Пустая строка» доступны также через контекстное меню строки.

Удаление выполняется мгновенно с undo-toast. Жёсткое подтверждение требуется только для группы с дочерними строками и для удаления нескольких выбранных строк.

## 5. Поля и данные заказа

### 5.1. Реквизиты заказа

| Поле | Обязательное | Правило ввода | Ошибка |
|---|---:|---|---|
| Номер спецификации | да | уникальная строка, без пробелов по краям | «Укажите номер» / «Такой номер уже существует» |
| Дата оформления | да | дата в локальном формате, хранение ISO | «Укажите дату» |
| Заказчик | да | существующий или новый по разрешённому сценарию | «Выберите заказчика» |
| Тип клиента | да | активное значение справочника | «Укажите тип клиента» |
| Статус | да | только доступные переходы | «Переход недоступен» |
| Основной комментарий | нет | многострочный текст | ограничение длины |
| В производство | нет | дата не раньше даты оформления | «Дата раньше даты оформления» |
| Плановая готовность | нет | дата не раньше даты оформления | «Дата раньше даты оформления» |
| Доставка | нет | переключатель | — |
| Адрес доставки | условно | обязателен при доставке | «Укажите адрес доставки» |

Номер спецификации и дата не должны исчезать при прокрутке или переходе между строками. Для даты допускается ввод с клавиатуры и выбор календарём; формат на экране — `ДД.ММ.ГГГГ`.

### 5.2. Строки спецификации

Тип строки определяет доступность полей:

| Тип | Обязательные поля | Расчёты |
|---|---|---|
| Группа | название | сумма и площадь дочерних товарных/сервисных строк |
| Товар | описание, количество, высота, ширина, цена за м² | площадь 1 ед., общая площадь, цена за ед., сумма |
| Услуга | описание, количество, цена за ед. | сумма |
| Комментарий | текст | не участвует в итогах |
| Пустая строка | нет | не участвует в итогах |

Неактуальные для типа строки поля визуально приглушаются и недоступны для Tab-навигации. Данные не удаляются при смене типа без предупреждения: если смена типа приведёт к потере значения, показать inline-предупреждение и дать «Отменить».

### 5.3. Формулы

```text
unit_area_m2   = height_mm * width_mm / 1_000_000
total_area_m2  = unit_area_m2 * quantity
unit_price     = unit_area_m2 * price_per_m2
total_price    = unit_price * quantity
service_total  = unit_price * quantity
group_total    = sum(child.total_price where child.is_calculated = true)
order_total    = sum(line.total_price where line.is_calculated = true)
balance        = total_amount - sum(payments.amount)
```

Расчёты выполняются на клиенте для мгновенного отображения и повторяются на сервере как источник истины. Итоги округляются только на границе отображения и хранения по правилам валюты; промежуточная площадь не должна преждевременно округляться до двух знаков.

### 5.4. Оплаты

Оплата не редактирует строки заказа и не меняет сумму заказа. В таблице оплат используются поля:

| Поле | Обязательное | Правило |
|---|---:|---|
| Дата | да | локальная дата |
| Тип | да | предоплата, финальный платёж, возврат, корректировка |
| Метод | нет | наличные, карта, банк, другое |
| Сумма | да | больше 0 для оплаты/корректировки; возврат хранится отдельным типом |
| Комментарий | нет | текст до установленного лимита |

Удаление платежа доступно только роли с правом управления оплатами и выполняется через undo-toast. Остаток пересчитывается сервером после сохранения платежа. Формат денег одинаков во всех строках: разделитель тысяч — пробел, десятичный разделитель — запятая, знак валюты — после числа.

## 6. Сохранение и статусная модель

### 6.1. Нижняя панель действий

На широком экране панель закреплена снизу рабочей области, на мобильном — превращается в обычный блок после таблицы. Слева показывается состояние сохранения, справа:

- «Сохранить»;
- «Сохранить и подтвердить» (если переход разрешён);
- «Отмена»;
- «Ещё» с печатью, экспортом и удалением.

«Сохранить» всегда доступна при изменениях, но блокируется на время запроса. Повторной отправки по двойному клику быть не должно.

### 6.2. Переходы статуса

В форме показывается только следующий допустимый переход для текущей роли и статуса. Для подтверждения заказа проверяются обязательные поля и наличие хотя бы одной расчётной строки. При уходе со страницы с несохранёнными изменениями показать стандартное предупреждение браузера.

### 6.3. Конфликты и ошибки

- ошибка поля показывается рядом с полем и не заменяется общим тостом;
- серверная ошибка сохранения отображается в шапке и около кнопки;
- после восстановления сети доступна кнопка «Повторить»;
- при конфликте версии заказа показать «Заказ изменён другим пользователем» и действия «Загрузить изменения» / «Оставить мои» (с обязательным просмотром diff перед перезаписью);
- нельзя терять локальные правки при `router.refresh()`.

## 7. Визуальный и контентный стандарт

### 7.1. Компоновка

- максимальная ширина рабочей области: 1440 px;
- базовый отступ между секциями: 20–24 px;
- поля в секции используют сетку 12 колонок на desktop, 2 колонки на tablet, 1 колонку на mobile;
- таблица занимает всю доступную ширину, а не узкую карточку;
- секции имеют короткий заголовок и одну строку пояснения только там, где без неё возможна ошибка.

### 7.2. Цвет и состояния

Использовать существующие токены приложения (`ink`, `muted`, `line`, `panel`, `accent`). Цвет не является единственным носителем смысла: статус дополнительно обозначается текстом и иконкой/меткой.

Состояния поля: обычное, hover, focus, disabled, error, read-only. Контраст текста и фона — не ниже WCAG AA. Красный цвет применяется только к ошибке или опасному действию.

### 7.3. Текст интерфейса

- подписи короткие и предметные: «Количество», «Цена за м²», «Плановая готовность»;
- единица измерения указывается в заголовке, а не вводится пользователем в число;
- не использовать «ОК», «Применить» без описания действия;
- сообщения об ошибках объясняют, что исправить: «Ширина должна быть больше 0»;
- действия называются глаголом: «Сохранить», «Добавить строку», «Удалить группу».

## 8. Адаптивность и доступность

- минимальная поддерживаемая ширина: 320 px;
- на mobile реквизиты идут одной колонкой;
- таблица не сжимает числа до нечитаемого состояния: используется горизонтальный scroll с видимым индикатором;
- клавиатурный фокус видим всегда;
- каждый контрол имеет `label`, доступное имя и сообщение ошибки через `aria-describedby`;
- таблица использует семантику `role="grid"`, `row`, `gridcell`, `columnheader` только если реализована полноценная grid-навигация; иначе использовать обычную семантическую таблицу с интерактивными полями;
- цветовые бейджи статуса имеют текстовую подпись;
- не блокировать масштабирование на мобильном.

## 9. Правила реализации

### 9.1. Состояние формы

Состояние формы хранит:

- `orderDraft` — реквизиты заказа;
- `lineDrafts` — строки в порядке отображения;
- `dirtyFields` и `dirtyLines`;
- `lastSavedSnapshot`;
- `saveState` (`clean`, `dirty`, `saving`, `saved`, `error`);
- `focusedCell` и выделенный диапазон.

Нельзя использовать только `defaultValue` для таблицы: после серверного сохранения и пересчёта UI должен получать актуальный snapshot без потери активного редактирования.

### 9.2. API-контракт

Предпочтительный контракт:

```http
POST  /api/orders                 # создать заказ и строки черновика
GET   /api/orders/:id             # загрузить форму целиком
PATCH /api/orders/:id             # сохранить реквизиты и пакет изменений строк
POST  /api/orders/:id/lines       # добавить строку, если нужен optimistic режим
PATCH /api/orders/:id/lines       # изменить строку
DELETE /api/orders/:id/lines      # удалить строку
POST  /api/orders/:id/status      # изменить статус
```

Каждый mutation-запрос должен принимать `clientVersion`/`updatedAt` для защиты от тихой перезаписи. Ответ содержит заказ, строки, итоги и новую версию.

### 9.3. Локальный черновик

При кратковременной потере сети форма сохраняет локальный черновик в `sessionStorage` с ключом заказа и временем. Локальный черновик не считается сохранённым на сервере; при повторном открытии показать предложение восстановить его. Не сохранять в браузере персональные данные дольше, чем это необходимо.

## 10. Нельзя

- разделять реквизиты и табличную часть по разным страницам;
- заставлять менеджера открывать модальное окно для каждой строки;
- сбрасывать форму после сохранения или обновления данных;
- скрывать ошибки только в тосте;
- разрешать редактировать расчётные поля как обычные числа;
- менять порядок колонок в зависимости от типа строки;
- удалять введённые значения без предупреждения;
- использовать автосохранение без видимого состояния сохранения;
- автоматически переводить заказ в новый статус при любом изменении поля;
- менять формат чисел между формой, печатью и Excel-экспортом.

## 11. Приёмочные сценарии

### Создание заказа

1. Пользователь открывает `/orders/new`.
2. Заполняет номер, дату и заказчика.
3. Добавляет группу и товарную строку, вводит значения с клавиатуры.
4. Нажимает «Сохранить черновик» или `Ctrl+S`.
5. Заказ сохраняется вместе со строками, URL меняется на `/orders/:id/edit`, введённые значения и фокус не теряются.

### Редактирование существующего заказа

1. Все реквизиты и строки загружаются одной операцией.
2. Пользователь меняет ячейку и переходит `Enter`/`Tab`.
3. Автосохранение показывает «Сохранение…», затем время сохранения.
4. Итоги изменяются сразу и совпадают с серверными после ответа.

### Вставка Excel

1. Пользователь копирует диапазон из Excel и нажимает `Ctrl+V` в первой ячейке.
2. Появляется предпросмотр с количеством строк и ошибками.
3. После подтверждения строки добавляются в правильном порядке и участвуют в расчётах.
4. Некорректные ячейки остаются подсвеченными и блокируют подтверждение до исправления.

### Ошибка и восстановление

1. Сервер отклоняет поле.
2. Ошибка показана рядом с конкретной ячейкой/полем, фокус переходит к ней.
3. Остальные изменения не теряются.
4. После исправления повторное сохранение отправляет только актуальные данные.

### Доступность

1. Вся форма проходится клавишей `Tab` в предсказуемом порядке.
2. Фокус визуально заметен.
3. Ошибку можно понять без цвета.
4. Основные действия доступны без мыши.

## 12. Definition of Done

Форма считается готовой, если:

- create и edit используют один компонент и один визуальный стандарт;
- реквизиты, таблица, итоги и действия доступны на одной странице;
- `Tab`, `Enter`, `Ctrl+S`, копирование и вставка TSV работают по спецификации;
- сервер повторяет все проверки и формулы;
- нет потери данных при refresh, ошибке сети или повторном сохранении;
- проверены desktop 1440 px, tablet 768 px и mobile 320 px;
- пройдены автоматические тесты формул/API и Playwright-сценарии из раздела 11;
- менеджер может занести типовой заказ без мыши и без открытия отдельного редактора строки.
